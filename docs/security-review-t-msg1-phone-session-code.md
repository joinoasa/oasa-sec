# Code review: T-MSG1 phone link, second part (session, messages, held packets)

**Status:** 2026-11-20 · **Kind:** internal security code review, written by an AI agent (Claude) that did not write the code; it does not replace a person's review, which AGENTS.md and the spec require before this moves past Draft · **Reviewed:** draft PR #42, branch `t-msg1-phone-session`, commit `62da9d1`

Threat-and-countermeasure level only: no exploit code. Spec: [oasa-sec-v0-phone-link.md](oasa-sec-v0-phone-link.md) v0.5 (§3, §4, §5, §6, §8, §10). Part 1's review: [security-review-t-msg1-phone-pairing-code.md](security-review-t-msg1-phone-pairing-code.md) (on its own branch).

## Scope and method

- **Code read in full:** `src/phone/session.rs`, `hold.rs`, `msg.rs`, `frame.rs`, `session_tests.rs`, and the changes to `radio.rs` (`store_failed`), `mod.rs` and `src/link/mod.rs` (`git diff t-msg1-phone-pairing...t-msg1-phone-session`). Read beside them: the link's handshake, data and timestamp paths in `src/link/endpoint.rs` and `session.rs` (what events it emits, when it saves, what it wipes), and `Radio`'s `fault`, `link_peer`, `pair_open`, `pinhole_reset` and completion.
- **Read against:** spec §3 to §6, §8 cases 1, 2, 13, 14, 16 to 22, 24, 26, 27, 30, §10, and the eleven spec questions in the PR body.
- **Run:** `cargo test --lib phone::` under a 3 GB memory cap, one thread: 152 tests pass.
- **Probes:** five throwaway tests in a scratch copy (not committed), to confirm S-1, S-2, S-4, S-9 and S-14 below. All loops bounded.
- **Mutations:** 10 single-line mutations of security checks, each run against `cargo test --lib phone::` and reverted (results below). The tree was left clean.

## Findings

No High findings. Line numbers are at `62da9d1`.

| ID | Severity | File:line | Finding | Suggested fix | Status |
|---|---|---|---|---|---|
| S-1 | Medium | `session.rs:856-875`, `733-741`, `531-548` | **Connections a new session left behind stay "completed" forever, and they can lock the owner out.** A `SessionEstablished` moves the session's binding to the connection its packet arrived on and marks that connection completed, but the connection it moved *from* stays completed. Nothing closes or displaces a completed connection except the bound one closing. The responder's session is established by the phone's first data packet after handshake 2, so whoever gets a copy of that packet to the radio first, on a connection of their own, takes the binding. Someone who can do that (a BLE relay, or selective jamming of the phone's packet plus injection; BLE's own security is not relied on, §3) can repeat it each time the owner connects. Each round leaves one more completed connection, and the owner's own connection never completes, so it is closed at 5 s. Once every slot is taken the owner gets `SlotsFull`, and that lasts until the stranger lets go: power-off or a reset are the only remedies. The probe showed this with 3 slots in 3 rounds. §6 says a stranger "cannot hold a connection slot against the owner's phone". While the binding is elsewhere, `RECEIVED` and `HELD` go to the stranger's connection and the packets count as handed over in that session (sealed, but the owner does not get them). Spec question 9 covers a packet that authenticates on another connection, not a session that is established on one. | When the binding moves, demote every other connection: `completed = false`, `since = now`, the same as `conn_gone` does. Then at most one connection is ever completed, and a stranger has to win every race, which is like jamming. Better still, bind a responder session only to the connection its accepted handshake 1 came from. Add a test: a new session's first packet arrives first on another connection, then assert that the old binding loses its slot rights | Open |
| S-2 | Medium | `session.rs:982-1004`, `hold.rs:33-35`, `session.rs:262-263`, `315-319` | **One held packet that cannot be sent stops `FETCH` for every packet after it, in every share.** `fetch` sends oldest first and `break`s at the first `send_received` that fails, putting that packet and all later ones back. If any held packet is too large for a `RECEIVED` at this MTU, every later packet, whatever its filter, cannot be fetched until that packet expires (24 h) or is pushed out. Anyone can make a packet that matches a filter (§5), so a single packet at the maximum size defeats the per-share isolation that §5 promises. Nothing ties `MTU` to `MAX_HELD_PACKET` plus the `RECEIVED` fields plus the link's 22 bytes: `boot` only asserts MTU ≥ 128. The PR's own test configuration (MTU 256, packets up to 256 bytes) has this property. The probe held three packets on two filters, the oldest 256 bytes long, and two `FETCH`es delivered none of them. | Check at `boot` that `MTU` fits `MAX_HELD_PACKET` plus the link overhead plus the largest `RECEIVED` header (let `BodyFormat` declare that header's size), or refuse in `offer` any packet whose `RECEIVED` would not fit. In `fetch`, skip a packet that cannot be sent (counted), don't stop. Add a test | Open |
| S-3 | Medium | `session.rs:273-274`, `324-325`, `779-780` | **The API invites one random stream to be shared by the link key and the public session indexes.** `RadioNode` needs `E: Entropy + Clone`. It hands one clone to `Radio` (which makes the link private key from it) and a fresh clone of its own, never-advanced copy to every new `Link` (which draws session indexes, sent in clear in packet headers, and retry jitter). If the firmware's `Entropy` is a value-type generator, such as a seeded stream cipher that derives `Clone`, which is common on microcontrollers, then every clone produces the same bytes. The link key's bytes then come back as public session indexes, a little more of the key with each rekey. Every reconnect also repeats the same index sequence, which ties sessions together on the air. All the `Entropy` types in the tree read the OS source, so the tests cannot see this. `S: Clone` is the same: it is correct only if every clone is a handle to the same flash. A store that caches state in each clone would leave old timestamps or filters readable after `erase_owner_state` runs on `Radio`'s clone. | Don't clone `E`: take one `Entropy` and lend it to each user (`&mut`, or one `Rc<RefCell<..>>` made inside the node), or take a factory that reads the hardware source each time. Until then, state on the type that clones of `E` must draw independent bytes and clones of `S` must share one flash. Add a test with a cloneable deterministic `Entropy` that asserts no two consumers draw the same bytes | Open |
| S-4 | Low | `hold.rs:263-268`, `457-465`, `session.rs:786` | **Hold numbers and session numbers restart at 1 on every boot,** so a hold number does not name the same packet across a power cycle. Suppose the phone fetched packet #1, the connection dropped before its `FETCH_ACK`, and the radio rebooted. The phone's next `FETCH` gets a different packet as #1. If the app then sends the `FETCH_ACK` it had queued for the old #1, the radio deletes the new packet unread. The probe confirmed this. It breaks "deletes those and no others" (§4) whenever the app acknowledges late, and the app cannot tell that the radio rebooted. | Start `next_hold` (and `session_no`) at a random value at boot, or add a per-boot epoch to the `RECEIVED` and `FETCH_ACK` bodies when `BodyFormat` is defined | Open |
| S-5 | Low | `hold.rs:400-419`, `508-512`; `session.rs:955-964` | **`FETCH_ACK` means two things** (PR question 6). It deletes, and any deletion also resets the wake back-off as "real". If the phone acknowledges junk to clear it, a flood keeps waking the phone every 10 s. If it acknowledges only real packets, junk stays up to 24 h, is counted in `HELD`, and is sent again in every new session, at a battery cost to the phone each time. Neither choice keeps both the back-off and a clean store, which is what §5 intends. | Spec: let the phone say which acknowledged numbers were real (a flag or a second list), or add a separate discard. Code: reset the back-off only on "real" | Open |
| S-6 | Low | `hold.rs:366-398`, `session.rs:948-954`, `625-629` | **A packet is handed over once per connection, not once per handshake.** The node's session number changes only when the bound connection closes (`rebuild`), never on a rekey. A `RECEIVED` that is lost, or that the app received and then lost (app crash), is not offered again until the connection drops. On USB, link packets are datagrams and the USB link can stay up for days, so a packet can sit unrecoverable until its 24 h expiry. Case 21's "delivered once after a handshake" reads as once per handshake. | Let `FETCH` offer every packet that has not been acknowledged (the phone drops duplicates by hold number), or bump the handover session on every `SessionEstablished` | Open |
| S-7 | Low | `session.rs:515-517` | **`link_opened` with an id that is already open does nothing.** If the firmware reuses a connection handle (BLE stacks do) and a disconnect event was lost or reordered, the new physical connection inherits the old one's `completed` flag, its session binding and its half-read frame. It then holds a slot that cannot be displaced and receives the owner's `RECEIVED`s (sealed). The code relies on a firmware rule that nothing states. | Treat a repeated `link_opened` as a close of the old connection followed by an open, or state the rule on the method and add a `debug_assert!` | Open |
| S-8 | Low | `session.rs:527-548`, `396-400`, `813-823` | **Link slots and the 5 s rule.** (a) BLE and USB share one pool of `LINKS` slots, so a flood of BLE connections can displace an incomplete USB network link, and the reverse (the pairing slots are separate, §10). (b) The 5 s rule is off during every window, a replace window included, so strangers can hold incomplete slots for up to 2 minutes while the owner's phone is moving to a new one. Displacement still frees a slot, so this is not a lock-out alone. (c) As with C-5 in part 1, a flood faster than `LINKS` connections per handshake round trip evicts the owner before its first data packet. `case_18` only floods before or after the owner connects. (b) is reasonable on BLE, where one connection carries both the pairing and the link characteristic (PR question 8), but neither the code nor the spec says so. | Count USB link slots apart from BLE ones; say in §3 why the 5 s rule is off in a window; test a flood interleaved with the owner's connect | Open |
| S-9 | Info | `session.rs:800-805`, `824-830`; `hold.rs:497-532` | **A faulted radio can still send a wake that was pending.** `fault` does not reset the `WakeLimit` or the hold store. The probe saw one `Wake` after a fault. The phone cannot connect, so this costs only battery. Held packets also stay in memory while the radio is faulted, though nobody can fetch them. `a_faulted_radio_holds_nothing` only covers a fault before anything was held. | Reset `wake` in `fault`, and decide (in the spec) whether a fault wipes held packets | Open |
| S-10 | Info | `hold.rs:46-48`, `196-207` | **Share sizes are small.** A kind with no filter wastes its third, so a phone with only index filters can hold at most 21 packets, not 64. | S-11 | Info | `session.rs:984-990`, `1014-1017`, `935-937` | Held packets are wiped when their slot is freed (`Entry::drop`), but their copies are not: `fetch`'s `sent` list, the `RECEIVED` plaintext in `send_received`, and the `Transmit`/`Settings`/`Update` bodies. ## Checked and found sound

- **The session is the link, unchanged.** The static key is the link key from the store, the one peer is the stored phone, and both are read only through `Radio::link_peer`, which gives nothing while unpaired or faulted. `link_config` matches §3. A handshake to the pairing key fails `mac1` (tested); a stranger is dropped as `untrusted_peer`, `bad_header` or `unknown_index` with no reply (tested).
- **Fail closed on storage.** Timestamps are saved before any handshake leaves or is answered (the link's order), and a failed save emits `Failure`, which faults the radio; no `Send` comes with it. A failed read at `Link::new` (boot, reconnect, trust re-check) faults. A failed filter write faults *before* the new filters are used. `Radio::fault` emits `EndAllSessions`, which closes every connection. The pinhole works while faulted (tested). Delivered plaintexts are wiped on the fault path too.
- **Trust changes.** Reset and replace end the session and close every link connection before any flash write, wipe held packets, filters (in memory) and the wake state, and rebuild the link from the store after `Paired` or `ResetDone`. A new connection re-reads the trust state and ends a session that no longer matches. Everything is serialised by the sans-IO design, so a message from the old phone cannot land between the trust write and the rebuild.
- **`PAIR_OPEN` caller trust.** Only `RadioNode` calls `Radio::pair_open`, with the session's own stored peer as `from`, and only for a body the link delivered (authenticated, replay-checked) of exactly 32 bytes. `radio()` returns `&Radio`, so firmware cannot call it through the node. Refused or not, it answers `StatusWanted`, as §4 says. The zero and label-secret refusals are tested through the session.
- **Types and direction.** Radio-to-phone types, unknown types, an empty body and a wrong `PAIR_OPEN` length are dropped and counted; control messages (`0x01`) are counted and do nothing; the firmware may send only `SENT` and `STATUS`. The radio originates nothing on the air: `Transmit` comes only from a phone `SEND` (case 27 tested).
- **No message keys on the radio.** The radio stores and forwards sealed packets and matches only public header fields; the handshake filter is the `mac1` key, a hash of a public key, checked with the existing `mac1_ok`. Nothing in the node decrypts, keeps or derives a messaging key.
- **Hold store bounds.** Fixed arrays; every loop is bounded (`offer` removes one entry per pass or returns; `fetch` at most 64 passes; `new_hold_number` ends within 65 tries because at most 64 numbers are taken). No indexing reachable from the air before a length check (`group_id` after `len ≥ 27`, `matches` before `copy_from_slice`); quotas divide only by a non-zero filter count; byte accounting cannot underflow. Expiry uses the node's monotonic clock with `saturating_add`, and `next_wakeup` includes it.
- **Flood isolation** within a share holds: room is made only in the packet's own share or from orphans (packets whose filter was removed), never from another current share (mutation killed). S-2 is the exception, on the *delivery* side.
- **Deframer.** A fixed buffer of `MTU` bytes; a length over the MTU or zero closes the connection, and nothing from a write that broke the framing is used. Partial frames wait; every split point is tested. No resynchronisation, which is correct for a stream.
- **Secrets.** `Debug` of `RadioNode`, `NodeAction`, `Filter`, `Filters`, `HoldStore`, `Deframer` and `FromPhone` shows no secret, body or handshake filter (tested for the replace secret, link private key and label secret). Delivered bodies are wiped after use; held entries are wiped on removal; the link's decrypted buffers are `Zeroizing`. `snow`'s state is not wiped (spec §7, known).
- **Replays** (case 2): same session, during the grace, after a rekey, after a reconnect; out-of-order copies count once.

## Not verified, and untested areas

- **Untested behaviour:** a new session established on a connection other than the bound one (S-1); the reset of other connections when the bound one closes (mutation survived); a held packet that cannot be sent, and so `fetch`'s rollback path (S-2); hold numbers across a reboot (S-4); a repeated `link_opened` id (S-7); a flood interleaved with the owner's connect, and BLE/USB slot sharing (S-8); a wake pending at a fault (S-9); a `FETCH_ACK` after a rekey within one connection; a write holding a good frame followed by a bad one; a cloneable deterministic `Entropy` (S-3).
- **`case_18_every_slot_completed_refuses_a_new_connection`** builds its three "completed" connections from one phone opening three sessions in turn. So the test passes only because of the stale completed flags behind S-1. Once S-1 is fixed, it needs another way to fill the slots.
- **Cases not covered by this PR** (as its body says): 23, 25, 28 (app and firmware); the app side of 6 and 7.
- A real `PhoneStateStore` on flash: that `erase_owner_state` removes timestamps and filters from flash (real-hardware check 7), and the write count per day (open question 8; filters add one write per `FILTERS`, so a hostile app can also wear the flash).
- Real BLE stacks: handle reuse (S-7), one connection carrying both the pairing and the link characteristic, and connection timing (real-hardware check 2).
- How the firmware supplies `snow`'s ephemeral randomness and the link's `Entropy` on the radio's chip (S-3, S-13).

## Verdict

The structure is sound. The radio fails closed on every storage error. Trust changes end sessions before any flash write. No path lets the radio learn a message key. No panic or unbounded loop is reachable from the air or the phone link. Two Medium findings break §5 and §6 promises against a stranger: S-1 (connection slots can be held against the owner) and S-2 (one packet blocks delivery for every filter). S-3 is an API hazard that could leak the link key under a common firmware choice. Fix those three, with tests, before this moves past Draft. The Low findings can follow, with the spec answers for S-4 to S-6.

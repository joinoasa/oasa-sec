# Security review: R-SEC2 roles, device removal and signing-key rotation

**Status:** v0.1, 2026-11-05 · **Kind:** internal review, written by an AI agent (Claude) from the code at `47170fb`; not an outside review · **Owner:** citruscybersec

Part of R-SEC2's release. The design is in [oasa-sec-v0-rotation.md](oasa-sec-v0-rotation.md); this page records what an independent read of the code found. It does not replace the human review the release record asks for. The R-SEC1 and R-COM2 reviews left R-SEC2 out; their findings are not repeated here.

## Findings

No high-severity finding. Two medium findings are to be fixed before R-SEC2 is marked done.

| ID | Severity | Finding | Fix | Status |
|---|---|---|---|---|
| M1 | Medium | **The signer never recovers from a lost autopilot link, and one empty datagram is enough to lose it.** The reader thread ends on any read error other than `WouldBlock`, `TimedOut` or `Interrupted` (`signer/port.rs:68`). A zero-length UDP datagram reads as 0 bytes, which `mavlink-core` reports as `UnexpectedEof`; a TCP link that the autopilot closes (an ArduPilot reboot on `tcpout:`, the setup `sitl.md:78` recommends) does the same. After that every tick fails with "autopilot link closed" (`port.rs:139`) or "Broken pipe"; the loop in `oasa-pair.rs:1143-1154` logs `signer_error` every 5 s forever, never reconnects and never exits, so a supervisor does not restart it. Rotations, including the one a removed operator asked for, never happen. The `udpout:` socket is bound to `0.0.0.0` and not connected, so anyone who can reach the drone's IP and find the port can send that datagram. Reproduced both: one empty datagram, then `rotate-signing`, then 20 s of `signer_error` and no rotation; a TCP server that closes once, then `Broken pipe` with no reconnect. | Treat a 0-byte read as nothing and keep reading. On a closed or failed link, reconnect with backoff (a new `UdpPort`), or exit non-zero so systemd restarts the signer; the first tick after either already probes. Connect the UDP socket to the autopilot's address (or drop frames from other sources) and bind it to the interface the autopilot is on. Test: a port that returns EOF, then a working one, and a rotation that still completes. | Open |
| M2 | Medium | **A failed rotation request is lost for good when an operator is removed.** `remove_key_locked` writes the tombstone (`removal.rs:313`), takes the operator out of the list (`:325`), and only then writes the rotation request (`:347-351`). If that write fails (disk full, a damaged generation file, a bad `rotation-pending`), the removal stands but nothing asks for a new key. Running `oasa-pair remove` again finds the peer no longer listed (`:308-309`), so it asks for nothing; an admin's resent entry is now `Known` (`:702-703`) and is acked. Reproduced both paths with the library: after the fault is cleared, the retry succeeds and `rotation-pending` stays empty. The removed operator's signing key keeps working on every path outside the link until someone runs `rotate-signing` by hand. `store::add` writes the request first for exactly this reason (`store.rs:286-305`); the spec says removing an operator "marks a signing-key rotation pending". | On a drone, write the request before the tombstone when the target is listed as operator (an extra request is harmless), as `store::add` does. Add the same fault test as `the_rotation_request_is_written_before_the_role_changes` for `remove_local` and `apply_entry`. | Open |
| L1 | Low | **The signer's "dedicated link" takes frames from anyone.** Besides M1, any host that reaches the signer's UDP port can inject frames (`port.rs:47-71`; the library's unconnected `udpout:` socket reads from every source). What that buys is limited by the code: signature times count only when they verify (`signer.rs:258-263`); only frames that verify under a key the signer holds decide the probe; the 3 s settle turns a forged old-key answer into `rotation_stuck`, never a rollback, while the autopilot signs its heartbeats. Two weaker spots remain. After every signer start `keyed` is false (`signer.rs:205`), so an unsigned "disarmed" heartbeat counts until the first signed frame arrives (`:270-277`); both autopilots refuse the key change while armed, so this ends in a rollback and a retry, not a change. And a removed operator who still holds the old key and reaches the port can keep a probe from rolling back. The spec describes "its own serial port or UDP port". | The connect and bind from M1. Say in the spec which hosts can reach the signer's port, and that the port must be on the companion's link to the autopilot only. | Open |
| I1 | Info | **An operator that missed a rotation gets only the pending key while the next one runs.** While `.next` exists, `owed` sends `NEXT` for the pending generation and nothing else (`rotation.rs:407-409`). An operator holding generation 1 when the drone is at 2 and has 3 pending stores 3 as pending and keeps 1, so it cannot sign for the autopilot until 3 commits or is dropped (then it gets 2, `:411`). Normally seconds; for as long as a rotation is `rotation_stuck`. Other operators are not affected. | Send the current key's `NEXT` and `COMMIT` first when the operator's commit is below the current generation, then the pending one; or let the operator keep a pending key per generation. | Open |
| I2 | Info | **Every control message reads both trust files before anything else.** `handle` calls `peer_role`, which runs `store::snapshot` (migration check, `trusted-peers.v1`, the whole `removed` file, up to 16 MiB), for every message from any trusted peer, including types it will drop (`control.rs:645-649`); an entry from an admin then reads `removed` twice more under the lock (`removal.rs:685`, `:792`). A trusted peer can spend the drone's CPU at link rate. | Cache the snapshot and reload it on the file watch (the program already watches both files), or check the type's role need first. | Open |

## Checked and found sound

- **Roles come only from a person.** The only writers of `trusted-peers.v1` are `store::add` (pairing and `trust`) and the two removal paths, which only take entries out (`removal.rs:325`, `:398`). No control message sets a role. Each message reads the sender's role fresh (`control.rs:645`), and `apply_entry` checks it again under the lock (`removal.rs:692-696`), so a removal that landed a moment ago counts for the next message.
- **Who may send what.** `REMOVE_ENTRY` only from an effective admin; `REMOVE_HEAD` from anyone else gets `NOT_ADMIN` and changes nothing; `REMOVE_HAVE`, `NOT_ADMIN` and `ACK` count only when their request id matches one in flight this session. `SIGNING_KEY_*` is taken only from a drone this device already holds a key file for, never by a device that is itself a drone, and only into that drone's files. A drone sends keys only to a peer whose role is `operator` right now (`control.rs:496-499`), so removed, demoted, admin and peer devices get nothing.
- **Tombstones win.** `snapshot` filters `removed` over the list; a removal appends the tombstone (fsync) before it edits the list, and a restore edits the list before it appends, so an unlocked reader never sees a removed key as trusted. `store::add` checks `removed` under the lock. The latest record per key decides; a restore never re-trusts by itself. `removed` is parsed strictly (a bad line is an error, which stops a starting `oasa-link` and makes a running one keep its last good state); only an unterminated last line is skipped, and the next append cuts it.
- **Two-admin rule.** A target that is admin on the receiving device needs votes from two different admins that are still valid there; the target and the device itself never count; one admin's second log does not count twice; votes from a removed or demoted admin are dropped; an admin cannot revoke itself, and entries for the device's own key are ignored.
- **Sync.** Union semantics: no entry undoes anything; order, loss and replays across sessions are harmless (exact entries are recognised by key, admin, log and seq; the link's replay window covers a session). A reset or lowered head restarts at 0. Received entries are never forwarded, so there are no loops and no amplification: each message gets at most one answer. The 4096-per-admin cap is hard and checked under the lock; refused entries are not acked.
- **Teardown.** `oasa-link` checks the files every 250 ms (mtime, size and inode, so in-place appends and atomic replaces are both seen) and at once on `SIGHUP`, drops all unsent control work for a removed peer, prints `peer_removed` and exits 3; a restarted process refuses the peer at start. Removing a drone on a ground station deletes all four of its key files.
- **Rotation files.** The highest generation is written before `.next`; `begin` refuses while `.next` exists; `commit` replaces the key, then its generation, then deletes `.next`, and each crash point loads to a defined state (checked by hand against `load_drone_keys`). A `.next` with no saved number, or a damaged key file, is an error, never deleted. Requests carry the generation, not a time, and a commit clears only the requests it answers. Demoting an operator writes the request before the role (`store.rs:286-305`). One signer per folder (`.signer.lock`).
- **The probe.** Only frames with the autopilot's system and component id count. A new-key frame decides for the new key; the old key is kept only after an old-key `COMMAND_ACK` for `MAV_CMD_REQUEST_MESSAGE` whose target fields name the signer (bytes 8 and 9 of the payload, checked against the message layout), no new-key frame within 3 s, and the autopilot seen signing something other than a `COMMAND_ACK`. Mixed or no evidence keeps both files. `SETUP_SIGNING` goes out only after a fresh, (once keyed) signed, disarmed heartbeat from the autopilot.
- **Timestamps.** Times from the autopilot link and from the tunnel count only when the signature verifies under a key the drone holds, and each is capped at the clock plus 60 s, in the signer and in `oasa-link`'s `mavlink-signing-ts`; the result over 48 bits is refused before a generation is used.
- **Secrets.** Keys never reach logs, errors or `Debug` (`SecretKey`, `SigningKey`, `Action` and `Control` hide them); `SIGNING_KEY_NEXT` bytes, the `SETUP_SIGNING` message and the raw frame are wiped after use; `SecretKey` compares in constant time; key files are 0600 and replaced atomically. The leftover copies the spec lists (library buffers, stack copies) were confirmed and are accepted as best effort.
- **Locking.** Every read-modify-write takes `.lock`; no path takes it twice (that would deadlock with `flock`); temp files have random names, so unlocked writers (`mavlink-signing-ts`) cannot collide.

## Risks that remain by design

- **A stolen admin** can remove every operator and peer on the devices that list it until it is removed, and each operator it removes starts a rotation. Its tombstones stay until a person restores them.
- **A vote never expires.** One honest admin's old vote plus one stolen admin's entry removes an admin. With fewer than three admins, remove a stolen admin by hand.
- **A demoted operator keeps its link session and its key until the rotation**, which waits for disarm; only removal ends the link. Roles are enforced by the signing key, not by the tunnel. Demoting by editing `trusted-peers.v1` by hand asks for no rotation; use `oasa-pair trust`.
- **Anyone who holds the current or pending key** can write frames that verify under it: an operator can make the signer commit early or keep a probe stuck, and can raise the timestamp floor by up to a minute.
- **The signer trusts the companion's clock.** A clock set far ahead (no RTC, spoofed time) moves the autopilot's signing time ahead with it.
- **While a trust file is unreadable**, `oasa-link` keeps its last good state, so new removals do not take effect on that device (`trust_unreadable`).
- **The device folder is trusted** (R-SEC1 L2): anyone who can write it can restore an old `removed` file or edit roles.

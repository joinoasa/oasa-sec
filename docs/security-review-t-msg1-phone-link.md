# Design review: T-MSG1 phone link

> **Note (2026-11-19):** the spec's pairing section was rewritten on 2026-11-19 for a radio with no button (v0.2); the findings table below describes the first draft (v0.1). A new independent review will be appended.

**Status:** v0.1, 2026-11-16 · **Kind:** internal design review, written by an AI agent (Claude) that did not write the spec; not an outside review, and no code exists yet · **Owner:** citruscybersec

Review of the first draft of [oasa-sec-v0-phone-link.md](oasa-sec-v0-phone-link.md). It does not replace the person's security review the task card asks for.

## Scope and method

The draft was read against the [pairing](oasa-sec-v0-pairing.md) and [link](oasa-sec-v0-link.md) specs and the code at `26b628f`: `src/link/{mod,endpoint,packet}.rs`, `src/pairing.rs`, `src/lib.rs`, `src/bin/oasa-pair.rs`. Nothing was run. The group and rotation specs were not read in full.

## Findings

Every fix below is a change to the spec's text. None has been tested: there is no code.

## Checked and found sound

- No new crypto: Noise `IK` and `IKpsk1`, X25519, ChaCha20-Poly1305, BLAKE2s.
- The radio never holds message keys or plaintext. Two phone key pairs is sound.
- A separate pairing prologue keeps phone and drone pairings apart.
- The label check with `IK` stops a swapped code. A stranger who only listens learns nothing.
- Rekey at 1 hour, reject at 90 minutes, keepalive timer off: accepted by `Config::validate`. The link still answers with keepalives as acknowledgements and still runs the stale rule.
- The handshake timestamp rule works on a responder with no clock: it only compares against the saved value.
- `mac1` keyed from a public key works as a filter (8 bytes; few chance matches).
- A replayed command inside a session is dropped by the 1024-packet window.
- A forged wake shows nothing, because the app handshakes and checks tags before alerting.
- The development-board caveat, and a taken-over phone being out of scope.

## Not verified

- nRF52840 BLE connection slots, and whether wake works with private addresses.
- The flash part's endurance.
- Whether the timestamp store keeps per-peer state a reset can clear.
- The changes made after this review have not been reviewed again.

## Second review: v0.2 pairing with no button (2026-11-19)

**Status:** v0.2 draft, 2026-11-19 · **Kind:** internal design review, written by an AI agent (Claude) that did not write the spec or v0.2's changes; it is not an outside review and does not replace the person's security review the spec and the task card require · **Subject:** [oasa-sec-v0-phone-link.md](oasa-sec-v0-phone-link.md) v0.2

### Scope and method

v0.2 was read in full against the [pairing](oasa-sec-v0-pairing.md) and [link](oasa-sec-v0-link.md) specs, the first review above, and the code at `b357fa8` it leans on: `src/pairing.rs`, `src/code.rs`, `src/identity.rs`, the `Attempts`, `claim` and `make_room` code in `src/bin/oasa-pair.rs`, `src/link/mod.rs` (`Config::max_future`) and the per-peer `FileTimestampStore`. The review was adversarial: for each rule it asked what an attacker with the label, an attacker with brief physical access, a hostile USB source, a bystander and a recording of the air can do. §11's claims for each v0.1 finding were checked.

**Nothing could be run against this.** No code exists for the phone pairing, the radio firmware or the app. The one thing measured: the QR version needed for the label text, with the `qrcode` crate this repo already uses (a scratch program, not committed). Attacks below are described at the level of threat and countermeasure only.

### Findings

Every suggested change is to the spec's text. None has been tested.

| ID | Severity | Finding | Suggested change to the spec | Status |
|---|---|---|---|---|
| R2-H1 | High | **"USB first" does not hold as written,** and it is the countermeasure §2.9, §2.7, §6 and §11 (H1, M6) rest on. (a) The 3 s head start runs from USB power, but before the phone's message 1 can arrive the radio must wake from storage mode and enumerate, and the app must find the device and get USB access (Android asks the user in a dialog). A real phone will often miss 3 s, and BLE is then open. (b) The rule "after a proving message 1 on USB, no more BLE" does not say it pre-empts a BLE attempt that already holds the window; under §2.4's hold rule the USB message 1 gets no reply and the BLE holder may complete. So the claim "cannot lose the window to BLE" is false in the likely case. (c) "Message 1 within 3 s of connecting" is undefined for USB (power, enumeration, or opening the interface). | Tie BLE to USB **enumeration**, not a timer: in a window opened by USB power, BLE pairing is refused while a USB host is enumerated, and opens only if no host enumerates within a stated time (a plain charger). A proving message 1 on USB **ends any BLE attempt that has not completed**, including a holder. Define "connecting" for USB as the host opening the pairing interface. Not verified. | State per platform whether cable pairing is available. If it is not on iPhone, say in §2.9 and §7 that iPhone owners rely on detection only, and add the platform question to §9 (MFi, or another race-free path). | R2-M2 | Medium | **A replace window hands the owner's held state to whoever completes.** §2.4 deletes only the old phone's key, sessions and timestamps on replace. The app fetches and acknowledges held packets before it sends `PAIR_OPEN`. Add to suite case 9 | Open |
| R2-M3 | Medium | **A replace window need not use the label secret at all.** It is opened inside an authenticated session by a phone that already trusts the radio, yet it accepts the static label psk, so everyone who ever saw the label can race it (§2.8's first bullet). This is avoidable without new cryptography. | In `PAIR_OPEN`, the old phone sends a fresh random 32-byte secret; the radio uses it as the psk for that window only and wipes it when the window closes. The old phone shows it as an R-SEC1-style one-time code (its own prefix) for the new phone to scan. Label holders then cannot race a replace window, and the USB-only flag becomes optional. | R2-M4 | Medium | **USB power edges and per-window state are undefined.** On an unpaired radio every appearance of USB power opens a window. The spec does not say whether a USB edge **during** an open window restarts the 2 minutes, the 3 s head start, the "USB seen, no BLE" flag, or the per-window `seen` set (a reset `seen` set lets recordings hold the window again). | Debounce: a window opens only after USB power has been absent for a stated time (for example 10 s) and present for a stated time. A USB edge during an open window changes nothing: no restart of the timer, the head start, the flags or `seen`. | R2-M5 | Medium | **The pinhole reset's interaction with windows and sessions is undefined.** (a) A reset with USB already present: rule 1 needs USB at start or USB appearing, so no window opens, while §2.8 says "the next USB power". (b) A reset during a replace window: the radio becomes unpaired with a window still open (and possibly BLE allowed). (c) A reset during a live session: §2.8 does not say the old phone's sessions end at once (§2.4 says so only for replace); the link keeps working sessions in memory until removal is noticed. (d) A reset between closing the window and writing the new peer. | State that a reset closes any window, ends every pairing attempt and every link session at once, clears `seen`, and opens a window only on the next debounced USB power edge (R2-M4). Write the replace as one atomic change of the trust file (old peer out, new in), as `store` already does. Suite cases for each of (a) to (d) | Open |
| R2-M6 | Medium | **Keeping the device key across reset leaves a silent path the spec says is closed.** §2.8 says a previous owner "cannot get in while the new owner stays paired". With `IK` they can pose as the radio to the new owner's phone and, by key compromise impersonation, as the owner's phone to the radio: drive it, fetch held packets, change filters, send `PAIR_OPEN`, and, because `max_future` is off on the radio, push a far-future handshake timestamp that locks the owner's phone out until a reset. ### Checked and found sound

- `Noise_IKpsk1` with psk at position 1 is R-SEC1's pattern, unchanged (`PAIRING_NOISE`; `pairing.rs` sets `psk(1, …)`). Message 1 (`e, es, s, ss, psk`) proves the psk and the phone's static key to the radio before any reply; message 2 (`e, ee, se`) proves the radio's static key to the phone, so a label holder without the radio's private key cannot pose as the radio.
- Identity hiding is as R-SEC1: the radio's key never travels; the phone's static key is hidden under `es`, so a passive listener (with or without the label) learns neither; only the radio's private key reveals it (R2-L11).
- Message 3 does close the replay hole: it is under keys that need the phone's ephemeral and static private keys, so a recorded message 1, from any window, can never complete. Knowing the psk alone decrypts nothing.
- Key compromise impersonation: the phone's radio-link key, if stolen, does not let anyone pose as the radio to that phone; the radio's key does work the other way, as the link spec says (R2-M6 for what that means here).
- Small-order keys: the label decoder pattern in `code.rs` refuses a small-order public key; `identity::is_small_order` covers all small-order encodings; `store` refuses them on save.
- A separate prologue (`"OASA-SEC v0 phone pairing"`) and a separate checksum label and prefix keep labels, R-SEC1 codes and drone pairings apart. R-SEC1's decoder refuses `OASAR1-` (the prefix check is exact up to case), and a stripped prefix would still fail the checksum.
- `BASE32_NOPAD` in `data-encoding` refuses non-zero trailing bits, so a changed last character is refused rather than decoding to the same bytes, as long as the label decoder uses it as `code.rs` does.
- Text length: 69 bytes in base32 is 111 characters, 118 with the prefix, all in the QR alphanumeric set. The 2⁻³² misread figure is right for a 4-byte checksum.
- One paired phone, and completion closing the window before the write, are sound; the detection argument of §2.7 holds given R2-M2 and R2-M5.
- Per-peer timestamps exist and can be deleted (`FileTimestampStore::new(dir, peer)`, removal deletes the file, `reset`), which settles the first review's "not verified" point. `Config::max_future` is `None` by default, so turning it off on the radio needs no code change.
- The light carries no security property, and the app is the authority; nothing depends on a user reading the light.
- §11's mapping of the v0.1 findings is accurate, except that H1's and M6's residual relies on USB first (R2-H1, R2-M1).
- "No new crypto" holds for the label checksum (R-SEC1's construction, new label), the hint (a truncated fingerprint) and message 3 (R-SEC1's confirm byte). R2-L2's suggested fix would be a new construction and is flagged as such.

### Not verified

- Whether an iPhone app can use a USB pairing interface without MFi (R2-M1), and how long a real Android phone takes from USB power to message 1 (R2-H1).
- nRF52840 BLE connection slots and whether "nobody can hold the port" works at BLE connection speeds (suite case 13 in simulation cannot show it).
- The behaviour of real power banks, chargers and phone power-role swaps on VBUS (R2-M4).
- Whether the chip's readout protection, the debug lock and the jig's commit step can be made to hold; the factory process; label wear and print quality.
- The QR result was measured with a uniform 118-character string, not a real label, and not scanned with phone cameras.
- No code, firmware or app exists, so no claim here is tested, and this review has not itself been reviewed.

## Checked and found sound

- No new crypto: Noise `IK` and `IKpsk1`, X25519, ChaCha20-Poly1305, BLAKE2s.
- The radio never holds message keys or plaintext. Two phone key pairs is sound.
- A separate pairing prologue keeps phone and drone pairings apart.
- The label check with `IK` stops a swapped code. A stranger who only listens learns nothing.
- Rekey at 1 hour, reject at 90 minutes, keepalive timer off: accepted by `Config::validate`. The link still answers with keepalives as acknowledgements and still runs the stale rule.
- The handshake timestamp rule works on a responder with no clock: it only compares against the saved value.
- `mac1` keyed from a public key works as a filter (8 bytes; few chance matches).
- A replayed command inside a session is dropped by the 1024-packet window.
- A forged wake shows nothing, because the app handshakes and checks tags before alerting.
- The development-board caveat, and a taken-over phone being out of scope.

## Not verified

- nRF52840 BLE connection slots, and whether wake works with private addresses.
- The flash part's endurance.
- Whether the timestamp store keeps per-peer state a reset can clear.
- The changes made after this review have not been reviewed again.

### Checked and found sound

- `Noise_IKpsk1` with psk at position 1 is R-SEC1's pattern, unchanged (`PAIRING_NOISE`; `pairing.rs` sets `psk(1, …)`). Message 1 (`e, es, s, ss, psk`) proves the psk and the phone's static key to the radio before any reply; message 2 (`e, ee, se`) proves the radio's static key to the phone, so a label holder without the radio's private key cannot pose as the radio.
- Identity hiding is as R-SEC1: the radio's key never travels; the phone's static key is hidden under `es`, so a passive listener (with or without the label) learns neither; only the radio's private key reveals it (R2-L11).
- Message 3 does close the replay hole: it is under keys that need the phone's ephemeral and static private keys, so a recorded message 1, from any window, can never complete. Knowing the psk alone decrypts nothing.
- Key compromise impersonation: the phone's radio-link key, if stolen, does not let anyone pose as the radio to that phone; the radio's key does work the other way, as the link spec says (R2-M6 for what that means here).
- Small-order keys: the label decoder pattern in `code.rs` refuses a small-order public key; `identity::is_small_order` covers all small-order encodings; `store` refuses them on save.
- A separate prologue (`"OASA-SEC v0 phone pairing"`) and a separate checksum label and prefix keep labels, R-SEC1 codes and drone pairings apart. R-SEC1's decoder refuses `OASAR1-` (the prefix check is exact up to case), and a stripped prefix would still fail the checksum.
- `BASE32_NOPAD` in `data-encoding` refuses non-zero trailing bits, so a changed last character is refused rather than decoding to the same bytes, as long as the label decoder uses it as `code.rs` does.
- Text length: 69 bytes in base32 is 111 characters, 118 with the prefix, all in the QR alphanumeric set. The 2⁻³² misread figure is right for a 4-byte checksum.
- One paired phone, and completion closing the window before the write, are sound; the detection argument of §2.7 holds given R2-M2 and R2-M5.
- Per-peer timestamps exist and can be deleted (`FileTimestampStore::new(dir, peer)`, removal deletes the file, `reset`), which settles the first review's "not verified" point. `Config::max_future` is `None` by default, so turning it off on the radio needs no code change.
- The light carries no security property, and the app is the authority; nothing depends on a user reading the light.
- §11's mapping of the v0.1 findings is accurate, except that H1's and M6's residual relies on USB first (R2-H1, R2-M1).
- "No new crypto" holds for the label checksum (R-SEC1's construction, new label), the hint (a truncated fingerprint) and message 3 (R-SEC1's confirm byte). R2-L2's suggested fix would be a new construction and is flagged as such.

### Not verified

- Whether an iPhone app can use a USB pairing interface without MFi (R2-M1), and how long a real Android phone takes from USB power to message 1 (R2-H1).
- nRF52840 BLE connection slots and whether "nobody can hold the port" works at BLE connection speeds (suite case 13 in simulation cannot show it).
- The behaviour of real power banks, chargers and phone power-role swaps on VBUS (R2-M4).
- Whether the chip's readout protection, the debug lock and the jig's commit step can be made to hold; the factory process; label wear and print quality.
- The QR result was measured with a uniform 118-character string, not a real label, and not scanned with phone cameras.
- No code, firmware or app exists, so no claim here is tested, and this review has not itself been reviewed.

### The residual in item R2-M6's answer: verdict

**Stated in kind, not in effect.** The admitted case is real and the conditions are right: it needs the pairing private key and the label secret (a memory read while the radio was out of the owner's hands), a BLE pairing in a USB window, and presence in range or a relay. A cable pairing and a replace pairing cannot be put in the middle (the replace secret is fresh, and the middle cannot make message 2 without it). What it gives is understated (R3-M1).

**Not strictly inherent to a radio with no button and no display, but nothing already in the design closes it.** The owner's phone has no channel to the radio that the middle cannot also speak on, except the cable (only where a cable path exists, open question 12) and the status light. Options, using only what oasa-sec already has:

- **Cable pairing.** Closes it where it exists. Unverified on every platform.
- **The phone's camera reads the light.** After completion the radio blinks out a long value from its pairing handshake hash (`snow` already exposes it), at least 128 bits with error detection, and the app compares it with its own. A middle runs two different handshakes and cannot make the hashes match. This needs no new cryptography: it compares two existing Noise handshake hashes, as channel binding does. It is a new feature (optical reading in the app, a blink encoder in the firmware), it takes seconds of holding the camera on the light, and it would be the first security property to rest on the light, against §2.6. Whether a phone camera reads a single status LED reliably is unverified. **A short code** (a few blinks the user compares by eye) **is not safe here**: the middle chooses one ephemeral key after seeing the other side's, so it can search for a match to a short value. Making a short code safe needs a commitment step, which is a new construction and the owner's decision under "no new crypto".
- **Re-keying at reset.** Impossible with a printed label and no other way to give the phone a new key; with the camera channel above it would be possible, and then that channel would carry the key itself, which is no better than the hash comparison.
- **Detection after the fact.** A tamper-evident cover over the label or case (open question 10) shows that someone had the radio open; it does not show a memory read through the case.

So: with only a printed label, BLE and a light nobody reads, it is inherent. The light read by the phone's camera, or a cable, would close it. Which to pursue is the owner's decision; until then the summary, §2.9 and §6 should say plainly that a radio that was out of its owner's hands can be put in the middle of its next BLE pairing.

### Checked and found sound

- **The link key in message 2 under `IKpsk1`.** Message 2's payload is encrypted under keys that mix `es` and `ss` from message 1, the psk, and `ee` and `se`. So the phone learns that the link key came from someone who holds the pairing private key and the psk, in reply to this phone's ephemeral and static keys. A replayed message 2 fails at the phone, because its ephemeral is new for each attempt. A passive listener, even with the label, cannot read the link key; only someone with the pairing private key can play the radio (R3-M1).
- **Binding.** The phone takes the link key at message 2; the radio binds it to the phone's static key only at a valid message 3, in one write with the peer. A phone whose attempt did not complete has a link key the radio does not hold, so its link handshake fails `mac1` and it gets no answer. Several attempts each get their own key, and only the completing one is kept (given R3-L1).
- **The link afterwards.** `mac1` is keyed from the receiver's public key (`packet::mac1_key`), and the radio's endpoint is built from its link identity, so a link handshake addressed to the pairing key fails `mac1`, as §3 says. New keys on both sides at each pairing mean fresh per-peer timestamps and no replay of old handshakes across pairings. Wake filters and the hold store do not use the link key.
- **No exclusive hold.** With message 2 giving nothing away and message 3 needing the phone's private keys, answering every proving message 1 is safe, and recordings can no longer hold the window. The first valid message 3 wins, and closing the window in memory before the write stops a second completion. A USB message 1 that ends BLE attempts is a clean pre-emption. The resource side needs R3-M2 and R3-L7.
- **The replace code.** The one-time secret is made by the old phone, travels only inside an authenticated session and on the old phone's screen, is refused in a USB window, and is wiped at the close. A label holder, or someone who read the radio's memory, cannot race or sit in the middle of a replace window without seeing the code. With no completion nothing changes. Erasing held state at completion answers R2-M2 (given R3-L2).
- **Debounce and rate limit.** These do bound windows from a flickering or toggled USB source. Edges inside a window change nothing, which closes R2-M4's restart questions. A distant attacker cannot open a window; they can only spend one (R3-M2, or jamming).
- **Pinhole reset.** It ends everything, wins against a pending write, and with USB present opens a window, which needs the radio in hand and so gives an attacker nothing new.
- **Stale terms.** "Button", "press", the USB-only flag and the exclusive hold appear only in the change list and in §11's history. The suite cases match the v0.3 text, except case 7 (R3-L5).
- **No new cryptography.** The per-pairing key uses the same X25519 key generation as `Identity::generate`. The replace code reuses R-SEC1's checksum construction under its own label and prefix. Message 2 gains a payload field. None of these is a new construction. This review's own suggestions keep to that, except the short blink code, which is flagged as needing one.

### Not verified

- Whether a phone camera can read the status light fast and reliably enough for the comparison in the verdict.
- The radio's real BLE connection slots, and handshake time on its chip under load (R3-M2, R3-L7).
- How the chosen flash store deletes (R3-M3); which store the firmware will use is not decided.
- How real chargers, power banks, car ports and phone power-role swaps behave against the debounce and the enumeration rule (R3-L4).
- Whether any phone can reach the CDC-NCM pairing port (open question 12), on which the only existing fix for the residual depends.
- No code, firmware or app exists, so no claim here is tested, and this review has not itself been reviewed.

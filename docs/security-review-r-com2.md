# Security review: the encrypted link (R-COM2, OASA-SEC v0)

**Status:** v0.1, 2026-11-05 · **Kind:** internal review, written by an AI agent (Claude) from the code at `704dce9`; not an outside review · **Owner:** citruscybersec

Part of R-COM2's release (oasa-lab `docs/release.md`: "Of the link protocol and implementation, in oasa-sec"). The design is in [oasa-sec-v0-link.md](oasa-sec-v0-link.md); this page records what an independent read of the code found.

## Scope and method

Commit `704dce9`: `main` plus the re-landed #9, #10 and #11 from open PR #19 (airtime-scaled timers, `src/link/timing.rs`). Read: the link spec, `src/link/` (every module), `src/bin/oasa-link.rs`, `src/mavguard.rs`, how `src/control.rs` rides the link, the file helpers the timestamp store uses, `snow` 0.10.0's handshake read path, and the lab's evidence (`docs/sdr-link.md`, the counted `l2-sdr-link` run `0e21d0f8787f` in oasa-lab PR #41). The group-key draft (`oasa-sec-v0-group.md`) is a spec only, with no code; it was not reviewed.

Run: `cargo test --locked --workspace` (338 passed), `scripts/link-e2e.sh` (24 checks passed, then it stopped on a script race, I5; the revoke checks after it did not run), and throwaway harnesses outside the repo using the library: 400,000 mutated handshake and data packets against an established pair, 2,000,000 random datagrams through the MAVLink guard (no panic; nothing delivered except one unmutated original), and timer runs for crossed handshakes and a blackout. Each finding was checked against the code.

## Findings

No high-severity finding. One medium finding is to be fixed before R-COM2 is marked done.

| ID | Severity | Finding | Fix | Status |
|---|---|---|---|---|
| M1 | Medium | **Crossed sessions are never rekeyed.** When both sides start a handshake at once, each answers the other, and each then promotes the session the *other* made on its first valid packet (`endpoint.rs:874-882`). Both now send on a session where they are the responder. Only the initiator of the current session rekeys (`endpoint.rs:958`), so nobody rekeys at `rekey_after`: the sessions run to `reject_after`, expire, and sends fail with `no_session` until a new handshake completes (a handshake round trip and the responder's switch; over 7 s on LoRa SF12). If both sides were started with `--initiate`, they cross again at each expiry, so this repeats for the life of the link. Reproduced with the library (rekey 60 s, reject 90 s): no handshake until 90 s, then send failures on both sides, crossing again at about 190 s. A one-off cross can also follow both sides firing the stale rule. The spec says crossed sessions last "until the next rekey" and "a rekey loses no packets"; neither holds here. The existing test (`tests.rs:765`) only checks delivery for 2 s. | Let either side start a handshake when its current session is older than `rekey_after` plus one retry, whoever made it (WireGuard's receive-side rule does the same for the initiator). Add a test with both sides initiating at once that runs past `rekey_after` and checks there is no send gap. | Open |
| L1 | Low | **The stale time only follows the retry; on a long-latency relay the default stays 30 s.** A side answers payload after half the stale time, so the stale time must be over twice the worst round trip (queueing included). Over the lab's SDR relay (35 to 70 s per round trip) the default 30 s made the initiator re-handshake every 10 to 60 s (oasa-sec PR #18, job `9325050e9d1a`); data still flowed, at the cost of airtime. #11 already covers this: `stale_after = max(30 s, 4 × retry)` and `retry ≥ 1.5 R + 2 s` (`timing.rs:187-199`) gives `stale/2 > 3 R`, so `--handshake-rtt-ms 70000` yields retry 107 s and stale 428 s, and `--retry-secs 90` yields stale 360 s. But the spec and the help define *R* as airtime only, and #18 (written before #11) sets `stale_after` directly, which could put it below 4 × retry (`validate` only asks for 2 ×, `mod.rs:162`). | For `l2-sdr-link`, pass `--handshake-rtt-ms` with the relay's measured worst round trip instead of `--stale-secs 180`. Say in the spec and help that *R* is the worst handshake round trip **including queueing and relays**, not only airtime. If #18 is still wanted, rebase it on #11 and make it raise-only (`max` with the derived value). | Open |
| L2 | Low | **The plaintext side checks the sender's IP, not its port** (`oasa-link.rs:1126`). With the default loopback setup any local process or user on that host can inject packets into the link. On a ground station the guard is off by default (no signing key), so injected guard-allowed commands (arm, take off, mode changes) reach the drone. | Accept only the `--plain-send` address and port once seen, or add `--plain-from HOST:PORT`; say in the spec that the host must not run untrusted local users. | Open |
| I1 | Info | The tunnel follows the peer to the source of any packet that authenticates (`oasa-link.rs:858-864`). Someone on the path who holds back a fresh packet and delivers it first from their own address moves outgoing traffic to themselves until the next real packet. They can read nothing; it is a blackhole they could already cause by dropping. Same as WireGuard. | None; note it in the spec. | Accepted |
| I2 | Info | Each reader thread copies whole datagrams (up to 64 KiB, `oasa-link.rs:611`) into a 4096-deep queue (`oasa-link.rs:1058`) before the MTU check, so a flood can hold about 256 MiB. | Drop datagrams over the MTU in the reader. | Open |
| I3 | Info | Control-layer notes are printed without the drop-line rate limit (`oasa-link.rs:929`). A trusted drone repeating `SIGNING_KEY_COMMIT` gets one log line per message. Trusted peers only. | Rate limit notes like drops. | Open |
| I4 | Info | Spec section 8 still says "Not tested: real radios". The counted `l2-sdr-link` run `0e21d0f8787f` now covers a handshake, data, replay, a changed packet and an untrusted identity over real RF (cabled). | Update section 8 and link the result. | Open |

The link does the right thing; the test does not. | `kill -HUP "$RD3" 2>/dev/null \|\| true`; rerun to cover the revoke checks. | Open |

## Checked and found sound

- **Crypto:** `Noise_IK_25519_ChaChaPoly_BLAKE2s` through `snow` 0.10 with the v1 prologue; no own crypto beyond `mac1` (keyed BLAKE2s, a filter). Small-order keys are refused wherever a peer key enters. `snow` does not check for an all-zero DH result, which IK does not need: message 1's chain mixes in `ss`, so a small-order ephemeral cannot forge either message without a static private key.
- **Indexes:** sender indexes travel only inside the Noise payloads; handshake 2's clear receiver index must equal the one inside (`endpoint.rs:705-707`). Local indexes are unique across all peers, handshakes and sessions, so there is no session confusion between peers.
- **`mac1` and limits:** constant-time compare; checked before the global bucket, the bucket before X25519, the per-peer gap only after Noise authenticates; per-source table bounded to 4096 addresses.
- **Timestamps:** strictly increasing per initiator; saved durably (temp file, fsync, rename, folder sync; owner-only, symlinks refused) before handshake 1 is sent or handshake 2 is answered; a failed save sends nothing. The optional future check reads the clock each time and does not save a refused value.
- **Replay window:** RFC 6479 with 32 words of 64 bits for a 1024-packet window, so the word being cleared never holds live bits; jumps over the ring clear it all; the window moves only after the tag verifies. Counter rebuilding works in `i128` and cannot overflow or underflow; counters at or past the receiver's packet limit are refused.
- **Nonces:** the send counter grows only after a packet is made and is never reused; sessions are never saved, so a restart always means a new handshake with fresh ephemerals. Rekey at 2³² packets, reject at 2⁶⁰.
- **Data header:** the index picks the key and the counter is the nonce, so any change fails the tag; the one exception (re-encoding a short counter as long) is a duplicate the window drops.
- **Session switching:** the responder sends on a new session only after valid data on it; a stale or replayed handshake cannot replace a working session; the previous session's grace counts only authenticated packets. The late-answer logic (#10) is safe: a forged handshake 2 fails its tag and `snow` restores its state on a failed read (checked in `snow`'s `handshakestate.rs`).
- **Amplification:** none. Handshake 1 (119 bytes) gets one 55-byte answer, and only from a trusted peer with a fresh timestamp; data is answered only after it authenticates; junk and untrusted peers get nothing.
- **Hostile input:** parsing checks fixed sizes before slicing; the fuzz runs above found no panic and no delivery of a changed packet. Time sums are safe because every setting is capped at ten years.
- **Timers (#11):** the derived retry exceeds *R* even after −20 % jitter; `validate` refuses contradictory settings; the round trip is clamped so nothing overflows. A forged or slow packet cannot hold a session up: only authenticated packets reset the stale and grace timers.
- **Secrets and logs:** our copy of the private key and every control plaintext are `Zeroizing`; `Debug` prints sizes only; logs carry reasons, counts and addresses, never contents; drop lines are limited to 10 a second with exact counts.
- **Sans-IO:** `src/link/` opens no sockets, starts no threads and reads no clock; index and jitter randomness is passed in, keys come from `snow`'s OS source.
- **Tunnel:** `--plain-listen` must be loopback unless `--allow-remote-plain`; every local packet gets content type `0x00`, so local programs cannot send control messages, and control messages never reach the plain side. The MAVLink guard parses every frame, checks CRC and length, and drops the whole datagram on anything else.
- **Lab evidence:** run `0e21d0f8787f` (checker PASS, counted): the air held only ciphertext, the replayed frame was dropped as `replay`, the changed frame as `bad_tag`, the stranger got `untrusted_peer` and no session; the handshake took 180.9 s over the relay.

## Risks that remain by design

- **Handshake replay DoS.** `mac1` uses a public key, so a recorded handshake 1 passes it and costs the responder an X25519 before `stale_handshake`, using up the 20 a second budget. Behind a radio bridge every packet has the bridge's address, so the per-source limit is shared with the real peer. Cookies are spec open question 2; jamming the radio is cheaper anyway.
- **A trusted peer is trusted:** its clock (a saved far-future timestamp locks it out until `oasa-pair reset-stamp`), and key-compromise impersonation as in any IK design until the key is removed.
- **`snow` does not wipe** its handshake or transport state, nor its copy of the static key; a memory dump can hold them.
- **No padding:** packet sizes and timing show which MAVLink messages are sent.
- **Handshake retries never stop** while the peer is away (backing off to `retry_max`), and the link does not enforce duty cycle; the radio layer must.
- **What the MAVLink guard cannot see:** `RC_CHANNELS_OVERRIDE` and `MANUAL_CONTROL` driving `RCx_OPTION`, `SYSTEM_TIME` moving the clock (in the spec).
